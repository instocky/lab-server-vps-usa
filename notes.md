Особенно удачна сама декомпозиция: Internet │ ▼ VPS :443 │ Caddy │ auth / timeout │ ▼ SSH reverse tunnel │ ▼ lab-server:8080 │ ▼ API Что здесь действительно важно 1. FRP не нужен. Если сервисов мало и API — обычный request/response HTTP, ssh -R закрывает задачу с минимальным количеством компонентов. 2. SSH здесь используется не как VPN. Это принципиальная разница в вашем контексте: lab-server ── исходящее SSH ──> VPS Никакой VPN-сети и никакого отдельного VPN-протокола для клиента. 3. Caddy на VPS — правильное место для внешнего периметра. Он принимает: https://api.example.ru и уже потом передаёт запрос в туннель. Это позволяет оставить приложение на lab-server вообще не озабоченным публичным доступом. 4. Таймауты действительно важны. Я бы только не воспринимал приведённые 5s/30s как универсальные значения. Потому что появляется очень простая эксплуатационная модель: SSH-туннель жив → API доступен. SSH-туннель умер → его надо автоматически поднять/дать alert. И тут я бы добавил ещё одну вещь к списку агента: systemd для самого reverse tunnel Не просто: Bash ssh -R ... а отдельный systemd service с: Restart=always; RestartSec=5; отдельным SSH-ключом; ServerAliveInterval; ServerAliveCountMax; ExitOnForwardFailure=yes. Тогда схема становится практически самовосстанавливающейся: VPS │ Caddy :443 │ ssh -R │ ╔══════▼══════╗ ║ lab-server ║ ║ systemd ║ ║ ↓ ║ ║ SSH tunnel ║ ╚══════╤══════╝ │ API :8080 И это уже очень симпатичный MVP production-ish архитектурный паттерн: один VPS, один SSH-туннель, Caddy, systemd и ваше приложение. При этом поверхность атаки маленькая: наружу фактически торчит только HTTPS на VPS и SSH, а сам API на домашнем сервере вообще не имеет входящего порта из Интернета.

Вариант B — отдельный SSH tunnel на каждый сервис SSH #1 → api1 SSH #2 → api2 SSH #3 → git Чуть больше процессов, зато сервисы изолированы друг от друга. Для нескольких сервисов я бы не усложнял и сделал один SSH-сервис с несколькими RemoteForward. И ещё важный момент: DNS вообще не требует отдельных IP. Можно сделать: api1.example.ru ─┐ api2.example.ru ─┤ git.example.ru ─┼──→ один VPS IPv4 grafana.example.ru┤ app.example.ru ─┘ Caddy смотрит на Host/SNI и отправляет запрос в нужный reverse tunnel. То есть один VPS + один публичный IP + один :443 → десятки ваших домашних сервисов. Это как раз сильная сторона такой архитектуры.

Caddy — принимает HTTPS и разводит домены по трём портам туннеля. DNS для трёх доменов → IP VPS. Открыть в firewall: 22/tcp — SSH; 80/tcp — Let's Encrypt/HTTP; 443/tcp — HTTPS. Схема: api1.example.ru ─┐ api2.example.ru ─┼─→ VPS :443 → Caddy api3.example.ru ─┘ │ ├→ 127.0.0.1:18081 ├→ 127.0.0.1:18082 └→ 127.0.0.1:18083 На lab-server Нужно: OpenSSH Client — обычно уже есть. Три ваших приложения: 127.0.0.1:8081 127.0.0.1:8082 127.0.0.1:8083 SSH-ключ для подключения к VPS. systemd service для поддержания туннеля. Сам туннель: Bash ssh \ -N \ -R 127.0.0.1:18081:127.0.0.1:8081 \ -R 127.0.0.1:18082:127.0.0.1:8082 \ -R 127.0.0.1:18083:127.0.0.1:8083 \ tunnel@VPS После его установления VPS получает: VPS:18081 → lab-server:8081 VPS:18082 → lab-server:8082 VPS:18083 → lab-server:8083 А Caddy: caddyfile api1.example.ru { reverse_proxy 127.0.0.1:18081 } api2.example.ru { reverse_proxy 127.0.0.1:18082 } api3.example.ru { reverse_proxy 127.0.0.1:18083 } Важная деталь Я бы обязательно оставил 127.0.0.1 в -R: -R 127.0.0.1:18081:127.0.0.1:8081 а не: -R 0.0.0.0:18081:... Тогда порты 18081–18083 не торчат непосредственно в Интернет. Единственный публичный вход — Caddy на 443. Итого: VPS lab-server SSH Server Client Caddy ✅ — HTTPS ✅ — DNS → VPS — приложения — ✅ reverse tunnel принимает устанавливает systemd tunnel — ✅ То есть на lab-server фактически не нужен ни FRP, ни VPN, ни nginx/Caddy для внешнего доступа. Caddy целесообразно держать именно на VPS. Если хотите, следующий шаг — могу дать полный минимальный конфиг: VPS + Ubuntu lab-server + systemd + SSH hardening + Caddy для 3 сервисов, чтобы это можно было буквально повторить по командам.
